## 1. 題材データの理解（このCSVは何者か）

- 出力元: **Super Build／SS7**（建築の一貫構造計算ソフト）。先頭行 `APP,Super Build／SS7,...`、2行目 `TITLE,東中延計画`（物件名）。
- 中身: **RC造（鉄筋コンクリート）の梁（大梁 G / 基礎梁 FB など）1本ごとの断面・配筋・応力・耐力のリスト**。いわゆる「梁断面リスト」。
- 規模感: 物件1棟ぶんで数百行。地上15階＋R階＋基礎、複数通り（Y0, Y1, Y2, Y3…）×複数スパン（X0-X1, X1-X2…）。

### データ構造の癖（パーサ設計に直結）
- **先頭2行はメタ情報**（APP行・TITLE行）。**3行目がヘッダ**、4行目以降がデータ。
- **1本の梁につき4行**で1セット:
  - `左端X+ / 左端X- / 右端X+ / 右端X-`
  - = 「梁の**左端・右端**」×「地震力の向き **X+ / X-**」の4通り。
  - **断面・配筋は4行とも同じ**で、**応力（M, Q）だけが向きで変わる**。→ 可視化では4行を1本に集約する前処理が要る。
- 梁の識別キー: `層(階) × フレーム(通り Y) × 軸1-軸2(スパン X) × 梁符号`。例: `1FL, Y0, X0, X1, 1G1`。
- 主なカラム群（60列超）:
  - 位置情報: 層 / フレーム / 軸1 / 軸2 / 梁符号
  - 材料: `Fc`（コンクリート設計基準強度 N/mm²: 54,45,36,33,30…階で逓減）
  - 形状: 梁スパン / 内法スパン / 梁幅 / 梁せい（例 600×2300、700×800）
  - 配筋: 上端筋・下端筋それぞれ **1〜3段**（鉄筋芯距離・本数・主筋径・鋼種・断面積）、スラブ筋
  - せん断補強: `STR総断面積 / STR間隔 / STR鋼種`（あばら筋・スターラップ。SD295A や SPR785 など）★要確認
  - 耐震壁の有無（上側・下側）
  - 耐力・応力: `Mbu(上)(下)`（終局曲げ耐力）/ 長期M / `Ds算定時 Q,M` / `保有耐力時 Q,M`
  - 降伏情報: `曲げ降伏STEP(左/右, 上/下)` `せん断降伏STEP`（保有水平耐力計算で、いつ・どこが降伏したか）★要確認
- 数値表記の癖: 先頭ゼロ省略（`.0` = 0.0）、マイナスゼロ（`-0.0`）、空セル多数（2段筋なし・降伏STEPなしなど）。

## 3. 可視化機能の候補（MECEに洗い出し）

優先度は付けず、まず全部出す。明日取捨選択する。

### 3-1. 整形テーブルビュー（基礎）
- 4行→1本に集約した一覧表。階・通り・符号でフィルタ/ソート/検索。
- 列の表示/非表示トグル（60列は多すぎるのでプリセット: 「形状」「配筋」「応力」など）。
- 同符号（例 全階の `G2`）のグルーピング表示。

### 3-2. 配筋断面図（梁を1本選んで断面を描く）
- 梁の矩形（幅×せい）に、上端筋・下端筋の主筋を丸で配置、あばら筋を矩形で。
- 段数・本数・径を図で表現。数表より圧倒的に直感的。

### 3-3. 伏図（平面）／軸組図（立面）上へのマッピング
- 通り芯グリッド（X0,X1… × Y0,Y1…）上に梁を線で描き、符号・断面を載せる。
- 階セレクタで各階の伏図、通りセレクタで軸組図（立面に各階を積層）。
- クリックで §3-2 の断面詳細へ。
- ★要確認: CSVには通り芯名はあるが**座標（mm）が無い**。スパン長から相対座標は組めるが、絶対配置には別データ（軸配置）が要るかも。

### 3-4. 応力・耐力チェックの可視化
- `保有耐力時M` と `Mbu`（終局耐力）の比＝余裕度をヒートマップ/バーで。
- 長期M・Ds算定時・保有時の応力をスパン方向にプロット（M図っぽく）。

### 3-5. 降伏ヒンジ / 崩壊メカニズム図
- `曲げ降伏STEP` `せん断降伏STEP` が入っている梁端を軸組図上にマーキング。
- **せん断降伏（脆性破壊）は赤**、曲げ降伏（靭性的）は別色 ── 危険箇所が一目で分かる。★要確認（構造的妥当性）
- 降伏STEP順のアニメーション（どの順で壊れていくか）も将来候補。

### 3-6. 物件サマリ / ダッシュボード
- 階数・通り数・梁本数、Fcの階別分布、断面寸法の種類、鋼種の内訳などの統計。

## 4. データモデル / パース設計

- パイプライン: `ファイル選択 → バイト読込 → エンコーディング判定 → CSVパース → 正規化(4行→1本) → 集約モデル → 各ビュー`。
- 正規化後の1梁モデル（イメージ）:
  ```
  Beam {
    id, 層, 通り(Y), スパン(X1-X2), 符号,
    形状: { Fc, スパン, 内法スパン, 幅, せい },
    配筋: { 上端: [{段, 本数, 径, 鋼種, 断面積}...], 下端: [...], スラブ },
    せん断補強: { 総断面積, 間隔, 鋼種 },
    耐力: { Mbu上, Mbu下 },
    応力: { 左端: {X+, X-}, 右端: {X+, X-} } // 長期M/Ds時/保有時のM,Q
    降伏: { 左端, 右端: {曲げSTEP, せん断STEP, 上下} }
  }
  ```
- パースは「ヘッダ名→キー」のマッピング表を1枚持つ（カラム名が日本語＆単位付きで長いため）。

## 5. ★今日の知見: 文字化け対策（パースの必須前提）

- **このCSVは Shift_JIS（CP932 / Windows-31J）**。SS7の標準出力エンコーディング。
- 素朴に `Blob.text()` や `fs.readFile(...,'utf-8')` で読むと**全部文字化けする**（今日それで詰まった）。
- 対策: **バイトで読んで自動判定デコード**する。
  ```ts
  function decodeText(buffer: ArrayBuffer): string {
    const b = new Uint8Array(buffer)
    if (b[0]===0xef&&b[1]===0xbb&&b[2]===0xbf) return new TextDecoder('utf-8').decode(b.subarray(3))   // UTF-8 BOM
    if (b[0]===0xff&&b[1]===0xfe) return new TextDecoder('utf-16le').decode(b.subarray(2))
    if (b[0]===0xfe&&b[1]===0xff) return new TextDecoder('utf-16be').decode(b.subarray(2))
    try { return new TextDecoder('utf-8',{fatal:true}).decode(b) }  // 厳格UTF-8
    catch { return new TextDecoder('shift_jis').decode(b) }          // ダメならShift_JIS
  }
  ```
- `TextDecoder('shift_jis')` はブラウザ標準でCP932にマップ。ファイル選択は `input[type=file]` → `file.arrayBuffer()` で。
- 将来: 文字化け時に手動でエンコーディングを切り替えるUIもあると安全。

## 6. 技術選定の論点（たたき台。明日詰める）

- **構成**: クライアント完結の静的SPA を推す。理由 → **構造計算データは機密。サーバーに送らずブラウザ内で完結**できれば設計事務所的に安心。ホスティングは静的（Vercel / Cloudflare Pages / GitHub Pages）。
- **FW**: React + TypeScript + Vite（既存スキルと揃う）。
- **CSVパース**: 自前パーサ（既存 `markdown-explorer` の `src/lib/csv.ts` が流用可）＋ §5のデコード。PapaParseでも可だがエンコーディングは自前デコード前提。
- **図形描画**: **SVG が第一候補**（構造図は線画中心・拡大/印刷に強い）。データバインドに D3、または素のReact+SVG。大量描画が重ければ部分的にCanvas。
- **表**: TanStack Table（フィルタ/ソート/列制御）。
- **状態**: 軽量（Zustand か React state）で十分。

## 9. 実装上の落とし穴メモ

- Shift_JIS必須（§5）。
- ヘッダは3行目（先頭2行はメタ、読み飛ばし）。
- 1梁=4行 → 集約前処理を必ず通す（生データのまま表に出すと4倍の行数で混乱）。
- 数値パース: `.0`→0、`-0.0`→0、空セル→null を明示処理。
- カラム名が日本語＋単位付きで長い（`上端スラブ筋sat( mm ^ 2 )` 等）→ ヘッダ→キーのマッピング表を持つ。
- 同符号の梁が複数階に出る → 「符号」だけでは一意でない。`階×通り×スパン×符号` で識別。
